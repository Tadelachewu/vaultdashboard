# Contact App Test with Dashboard

This repo contains a small Vault-based “app onboarding” system:

- **backend/**: Express API that creates Vault AppRoles + policies per app, stores an app registry, and enforces role/ownership rules.
- **admin-ui/**: React dashboard for developers/admins (login-based).
- **contact-app/**: Example Node script that logs into Vault with an AppRole and reads secrets for a single app.

## Features

- **Login-based UI**
  - **developer**: can create apps and can edit/delete only apps they created
  - **admin**: can view all apps + details (read-only)
- **Apps listing**
  - Developers see only their own created apps
  - Admin sees all created apps
- **Ownership enforcement (backend)**
  - All write actions require developer role and ownership checks
  - Admin cannot perform write actions (read-only access)

## Prerequisites

- Node.js + npm
- A running HashiCorp Vault server reachable from the backend
- Vault must have:
  - **KV v2** secrets engine mounted at `kv`
  - **AppRole** auth method enabled
  - A management token with permission to create policies and approle roles (backend uses this token)

## Vault setup (example)

If you are using the Vault CLI, a typical setup looks like:

```bash
vault server -dev
vault auth enable approle
vault secrets enable -path=kv kv-v2
```

## Configure environment variables

### backend/.env

Create/update `backend/.env`:

```env
PORT=3001
VAULT_ADDR=http://127.0.0.1:8200
VAULT_TOKEN=REPLACE_WITH_MANAGEMENT_TOKEN
AUTH_SECRET=REPLACE_WITH_RANDOM_SECRET
```

Optional user configuration:

- `USERS_JSON`: JSON array of users for login. Supports either plaintext `password` or `passwordHash` + `salt`.

Example (plaintext passwords):

```env
USERS_JSON=[{"username":"admin","password":"admin123","role":"admin"},{"username":"dev","password":"dev123","role":"developer"}]
```

If `USERS_JSON` is not set, these defaults are used:

- `admin / admin123` (role: admin)
- `dev / dev123` (role: developer)

### contact-app/.env (example client)

`contact-app` logs into Vault using an AppRole generated by the backend.

```env
VAULT_ADDR=http://127.0.0.1:8200
ROLE_ID=...from the dashboard...
SECRET_ID=...from the dashboard...
APP_NAME=your_app_name
```

## How it works

### What “creating an app” means

Creating an app in the dashboard does not generate a new Node/React project. It creates Vault configuration for that app:

- a Vault AppRole (so the app can authenticate)
- a Vault policy (so the app can only read its own secrets)
- a registry entry (so the dashboard can list it and enforce ownership)

### App creation

When a developer creates an app:

- A Vault policy is created: `<appName>-policy`
- A Vault AppRole is created at: `auth/approle/role/<appName>`
- The backend returns:
  - `role_id`
  - `secret_id`
- An internal **app registry entry** is stored in Vault KV:
  - Path: `kv/_registry/apps/<appName>`
  - Data includes: `owner`, `createdAt`, `role_id`

### Secrets storage

Secrets are written per app at:

- `kv/<appName>/config` (KV v2 data path)

### Where data is stored

This project uses Vault for both secrets and small amounts of metadata.

**Vault KV (data)**

- App registry (created apps + details): `kv/_registry/apps/<appName>`
  - example fields: `owner`, `createdAt`, `role_id`
- User registry (admin-created users): `kv/_registry/users/<username>`
  - example fields: `role`, `salt`, `passwordHash`, `createdAt`, `createdBy`
- App secrets (your key/value secrets): `kv/<appName>/config`
  - keys are whatever you save in the UI (ex: `stripe_key`, `email_user`, `email_pass`)

**Vault auth/system (configuration objects)**

- AppRole per app: `auth/approle/role/<appName>`
- Policy per app: `sys/policies/acl/<appName>-policy`

**Not stored in Vault**

- The AppRole credentials for a running service (`ROLE_ID`, `SECRET_ID`, `VAULT_ADDR`, `APP_NAME`) are usually stored in that service’s runtime environment (deployment env vars, secrets manager, or local `.env` for development).

### Roles and permissions

- **developer**
  - can create apps
  - can add/rotate secrets
  - can regenerate secret IDs
  - can delete an app
  - only for apps where `owner === username`
- **admin**
  - can list and view app registry entries
  - cannot create/edit/delete apps (read-only)

### Admin registering users

Admins can create users from the dashboard. Those users are stored in Vault KV at:

- `kv/_registry/users/<username>`

Passwords are stored as `passwordHash` + `salt` (not plaintext).

## API endpoints (backend)

Auth:

- `POST /auth/login` → `{ token, user }`
- `GET /me` → current authenticated user

Apps:

- `GET /apps` → list apps (scoped by role)
- `GET /apps/:appName` → app details (scoped by role)
- `GET /apps/:appName/secrets` → read secrets for an app (scoped by role)
- `POST /create-app` (developer only)
- `DELETE /apps/:appName` (developer + owner only)

Secrets (developer + owner only):

- `POST /add-secret`
- `POST /add-secrets-batch`
- `POST /rotate-secret`
- `POST /regenerate-secret-id`

All protected endpoints require:

```
Authorization: Bearer <token>
```

## Preparing a service to use an app’s secrets

Any Node/Express service can consume secrets created by this dashboard by following this standard flow:

1. Set environment variables in the service:
   - `VAULT_ADDR`
   - `ROLE_ID`
   - `SECRET_ID`
   - `APP_NAME` (must match the created app name)
2. Login to Vault using AppRole:
   - `POST /v1/auth/approle/login`
3. Read secrets from KV v2:
   - `GET /v1/kv/data/${APP_NAME}/config`
4. Use the returned keys in your app (SMTP creds, payment keys, etc).

### Minimal Node pattern (axios)

```js
require("dotenv").config();
const axios = require("axios");

const VAULT_ADDR = process.env.VAULT_ADDR;
const ROLE_ID = process.env.ROLE_ID;
const SECRET_ID = process.env.SECRET_ID;
const APP_NAME = process.env.APP_NAME;

async function getVaultToken() {
  const res = await axios.post(`${VAULT_ADDR}/v1/auth/approle/login`, {
    role_id: ROLE_ID,
    secret_id: SECRET_ID,
  });
  return res.data.auth.client_token;
}

async function getAppSecrets() {
  const token = await getVaultToken();
  const res = await axios.get(`${VAULT_ADDR}/v1/kv/data/${APP_NAME}/config`, {
    headers: { "X-Vault-Token": token },
  });
  return res.data.data.data || {};
}
```

### Example secret keys

- Contact service (Nodemailer): `email_user`, `email_pass` (optional `email_to`)
- Payment service: `stripe_key`

## App name rules

App names must match:

- 2–63 characters
- start with alphanumeric
- allowed: letters, numbers, `_`, `-`

Examples: `contact`, `my_app-1`

## Security notes

- Do not commit real Vault tokens or production credentials.
- Set `AUTH_SECRET` to a strong random value in real environments.
- Prefer hashed passwords via `USERS_JSON` when using this beyond local testing.
- Avoid printing secrets to logs in real apps.

## Troubleshooting

- **409 App already exists**: app name is already registered.
- **403 Forbidden**: you are not the owner (developer) or you are an admin trying to do a write action.
- **Vault 404 errors**: ensure KV v2 is mounted at `kv` and AppRole auth is enabled.
